# SEO Audit Log — Tanzania Sensational

## 2026-05-05 — Session 1: Initial Audit & Quick Wins

### Changes Made

#### 1. Sitemap Expansion
- **File:** [`resources/views/sitemap.blade.php`](resources/views/sitemap.blade.php)
- **What:** Added `<lastmod>`, `<changefreq>`, and `<priority>` elements to each URL entry
- **Before:** Only `<loc>` was present per URL
- **After:** Each URL now includes `<loc>`, `<lastmod>`, `<changefreq>`, `<priority>`
- **Why:** Google uses `<lastmod>` to determine recrawl frequency. Without it, fresh content may not be crawled promptly. Priority helps Google understand which pages are most important.
- **Expected impact:** Faster discovery of new/updated content, better crawl budget allocation

#### 2. Sitemap Route Enhancement
- **File:** [`routes/web.php`](routes/web.php:106-195)
- **What:** Restructured sitemap generation to include `lastmod` (from model `updated_at`), `changefreq`, and `priority` for each URL type
- **Priority assignments:**
  - Homepage: 1.0 (weekly)
  - Trekking routes: 0.9 (weekly)
  - Safari packages: 0.9 (weekly)
  - Safaris listing: 0.9 (weekly)
  - Blog listing: 0.8 (weekly)
  - Destinations: 0.8 (monthly)
  - Blog posts: 0.7 (monthly)
  - About/Group Departures: 0.7 (weekly/monthly)
  - Company pages: 0.6 (monthly)
  - Contact/Gear Checklist: 0.6 (monthly)
  - Safari guide pages: 0.5 (monthly)
- **Why:** Different page types have different business value and update frequency. Trekking routes and safari packages are high-value commercial pages that should be crawled more frequently.
- **Expected impact:** Improved crawl efficiency, Googlebot prioritizes commercial pages

#### 3. robots.txt Update
- **File:** [`robots.txt`](robots.txt)

- **Expected impact:** Reduced crawl waste, cleaner index

#### 4. H1 Hierarchy Fix on Safari Guide Pages

- **Why:** Every page must have exactly one `<h1>` containing the primary keyword. This is a fundamental HTML accessibility and SEO requirement.
- **Expected impact:** Improved heading hierarchy, better semantic structure for screen readers and search engines

#### 5. Organization Schema Expansion
- **File:** [`routes/web.php`](routes/web.php:295-316)
- **What:** Expanded Organization JSON-LD schema from 4 fields to 12+ fields
- **Before:**
  ```json

    "@type": "Organization",
    "name": "Tanzania Sensational",
    "url": "https://tanzaniasensational.com"
  }
  ```
- **After:**
  ```json
  {
    "@context": "https://schema.org",
    "@type": "Organization",
    "name": "Tanzania Sensational",
    "url": "https://tanzaniasensational.com",
    "logo": "https://tanzaniasensational.com/logo.png",
  ```

- **Why:** Rich Organization schema is a strong E-E-A-T signal. It enables Knowledge Panel features, validates business legitimacy, and provides structured contact info to search engines.
- **Expected impact:** Stronger E-E-A-T signals, potential Knowledge Panel eligibility, improved trust signals

#### 6. HTTPS Redirect
- **File:** [`.htaccess`](.htaccess)
- **What:** Added HTTP → HTTPS 301 redirect rule
- **Before:** No HTTPS enforcement in `.htaccess`
- **After:** `RewriteCond %{HTTPS} off` → `RewriteRule ^(.*)$ https://%{HTTP_HOST}/$1 [R=301,L]`
- **Why:** HTTPS is a ranking signal. All traffic should be served over HTTPS to prevent security warnings and consolidate link equity.
- **Expected impact:** Consolidated ranking signals, improved security perception

### Changes Made

#### 1. `.env` — Switched default connection to SQLite
- **File:** [`.env`](.env:23)
- **Before:** `DB_CONNECTION=mysql`, `DB_HOST=127.0.0.1`, `DB_PORT=3306`, `DB_DATABASE=TSS`, `DB_USERNAME=root`, `DB_PASSWORD=`
- **After:** `DB_CONNECTION=sqlite` (MySQL config commented out)
- **Why:** SQLite requires no server process, no credentials, no separate database setup. The entire database is a single file.

#### 2. `database/database.sqlite` — Created SQLite database file
- **File:** [`database/database.sqlite`](database/database.sqlite)
- **What:** Empty SQLite database file created at `database/database.sqlite`
- **Why:** Laravel expects this file to exist for SQLite connections

#### 3. `database/migrations/2026_03_17_130000_add_capacity_and_holds_to_departures_table.php` — Guarded MySQL-specific raw SQL
- **File:** [`database/migrations/2026_03_17_130000_add_capacity_and_holds_to_departures_table.php`](database/migrations/2026_03_17_130000_add_capacity_and_holds_to_departures_table.php:26)
- **What:** Wrapped `DB::statement()` with raw MySQL UPDATE in a `DB::getDriverName() === 'mysql'` guard
- **Why:** The raw SQL uses MySQL-specific `CASE` syntax. SQLite doesn't need this data migration since it's a fresh database.

#### 4. `database/migrations/2026_03_16_130755_create_bookings_table.php` — Made `departure_id` nullable from the start
- **File:** [`database/migrations/2026_03_16_130755_create_bookings_table.php`](database/migrations/2026_03_16_130755_create_bookings_table.php:13)
- **Before:** `$table->foreignId('departure_id')->constrained()->cascadeOnDelete();`
- **After:** `$table->foreignId('departure_id')->nullable()->constrained()->cascadeOnDelete();`
- **Why:** SQLite doesn't support `->change()` to alter column nullability. Making it nullable from the start avoids the need for the `->change()` call in the later migration.

#### 5. `database/migrations/2026_03_16_221356_add_safari_booking_fields_to_bookings_table.php` — Removed `->change()` call
- **File:** [`database/migrations/2026_03_16_221356_add_safari_booking_fields_to_bookings_table.php`](database/migrations/2026_03_16_221356_add_safari_booking_fields_to_bookings_table.php:23)
- **What:** Removed `$table->foreignId('departure_id')->nullable()->change();` since `departure_id` is now nullable from the base migration
- **Why:** SQLite cannot execute `->change()` on column definitions

#### 6. `.env.example` — Updated to reflect SQLite as default
- **File:** [`.env.example`](.env.example:23)
- **What:** Added comment block explaining how to switch back to MySQL
- **Why:** Documentation for future developers

### Post-Deployment Fix: API 500 Errors (Scrambled Data)
After the MySQL driver error was resolved, API endpoints (`/api/trekking-routes`, `/api/departures`) returned 500 errors.

#### Diagnosis
The import script (`scripts/import-mysql-dump-to-sqlite.php`) used positional column mapping via `PRAGMA table_info`, but the MySQL dump column order differs from the SQLite schema because:
1. **Later migrations add columns at the END of SQLite tables** — SQLite cannot insert columns in the middle
2. **MySQL migrations use `->after()`** to position columns in the middle of the table
3. This caused a column order mismatch where data was mapped to wrong columns

#### Tables Affected
| Table | Root Cause | Columns Misaligned |
|-------|-----------|-------------------|
| `departures` | `total_seats`/`held_seats` at end of SQLite vs middle in MySQL | `departure_date`, `return_date`, `available_seats`, `status` had wrong data |
| `trekking_routes` | `editorial_image`/`editorial_image_2`/`editorial_content` at end of SQLite vs middle in MySQL (positions 12-14) | `success_rate`, `highlights`, `inclusions`, `exclusions` shifted by 3 positions |
| `blog_posts` | `meta_title`, `meta_description`, `content_html`, `category` added via `->after()` which SQLite ignores | All 12 blog posts had timestamps in `meta_title`, image URLs in `created_at`, etc. |

#### Fix Applied
Created per-table fix scripts with explicit SQLite→MySQL column position mapping:
- [`scripts/fix-departures-import.php`](scripts/fix-departures-import.php) — 30 rows re-inserted with correct column mapping
- [`scripts/fix-trekking-routes-import.php`](scripts/fix-trekking-routes-import.php) — 16 rows re-inserted with editorial columns mapped to end
- [`scripts/fix-blog-posts-import.php`](scripts/fix-blog-posts-import.php) — 12 rows re-inserted with correct `->after()` compensation

All 58 affected rows across 3 tables were re-inserted with correct data. The fixed `database/database.sqlite` was committed and pushed to git.

2. `php artisan optimize:clear`

4. Verify API endpoints return 200 OK
